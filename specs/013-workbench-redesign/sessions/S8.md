## Rules that bit this feature (still true)

- `tasks.md`: flip checkboxes and add **new** lines starting `  →` only. Never
  reword an existing line — the hook halts on the whole uncommitted diff, so
  commit bookkeeping before any other edit.
- Two subagents must not commit into the worktree at once. Reviewers
  (read-only) can run beside a coding subagent; anything that commits is
  serialised. Phase 4's pattern, which worked: three parallel red-test
  dispatches on disjoint files (none committing), then the implementation
  dispatch commits them all.
- **Pin the module contract before parallel dispatches.** Phase 3 and phase 4
  both wrote one scratch file naming every store field, prop, `data-*`
  attribute and string before a line was written, and both times the tests and
  the implementation agreed on first contact. Where the contract is silent the
  tests decide, and the implementer follows them: phase 4's `data-selected-*`
  ended up on the root `section` for exactly that reason.
- A dispatch that may not edit tests will contort the source to avoid it.
  Phase 4's implementer made two `CenterView` props optional with no-op
  defaults rather than touch two out-of-scope test files; the review caught it
  and the follow-up made them required. If a task legitimately needs a
  pre-existing test updated, say so in the dispatch and name the file.
- Subagents run commands as `(cd <worktree> && …)`; the smoke run starts the
  worktree's own dev server on 5174 (`pnpm dev --port 5174 --strictPort`) with
  `SMOKE_BASE=http://localhost:5174/piste-planner/`. A fresh worktree has no
  `node_modules` — `pnpm install` first.
- Reviews after every task that adds tests or touches `.tsx`; bundle the fixes
  into one dispatch that commits as a `follow-up`.
- The editor's diagnostics panel mixes the main checkout against worktree
  types; ignore it, `tsc -b` in the worktree is the check.
- Standing rule 13: every panel and the canvas are styled to the mockup as
